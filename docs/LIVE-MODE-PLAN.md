# Live mode — plan

A market day the vendor is trading *right now*: the storefront leads with the market it is
standing in, the day's menu carries per-dish availability, and the vendor closes the day when
they pack up. Wireframe: `tmp/live-mode.png` (its logo and *bientôt épuisé* tag are not the
design).

Slice 0 shipped. Slice 1 is built through HTTP — both availability events, the today-guard,
`soldOutItemIds` on the read model and both query payloads, `inProgress` on the occurrence, the
sort fix, and the idempotent availability route — with the vendor and customer UI and the ops
alert still to come.

## Shape

What gets built, in order. Why is in the decisions below.

**Slice 0 — `/carte`. Done.** `app.routes.ts` is a componentless parent holding
`storefrontResolver`, children `''` → `StorefrontPage` and `'carte'` → `CartePage`; a *Notre carte*
row on the home page. Three things the plan did not call:

- **The metadata card moved from `StorefrontPage.ngOnInit` into the resolver.** It was the only
  call site, so `/carte` would have shipped with the fallback `<title>`; in the resolver it covers
  every route under the resolve and the lifecycle hook goes away. Both pages get the same card —
  a per-page title is skipped, duplicate across two pages of one site, not worth a branch at one
  vendor.
- **The carte renders `DishCard`, and `DishRow` is deleted.** Rows existed only to stop the carte
  and the day's menu competing on size on one page; separate pages ended that. Photo-less dishes
  get a `bg-canvas` panel with the fork-and-knife, on the card and in the sheet.
- **`app.routes.spec.ts` fakes `HttpBackend` rather than using `HttpTestingController`** — a
  resolver runs inside the navigation, so flushing by hand races the router. It also counts
  requests, which is what proves one fetch serves both children.

**Slice 1 — sold-out, end to end.**

| | |
|---|---|
| Event | `ItemMarkedAsAvailable`, mirroring `ItemMarkedAsSoldOut` |
| Aggregate | `markItemAsAvailable`; both guarded to *today* |
| Read model | `market-day-view` gains `soldOutItemIds`; store gains `markSoldOut` · `markAvailable`; `setMenu` intersects `sold_out` with the new `itemIds` |
| Query | availability joins onto the occurrence; `inProgress` moves onto the occurrence; occurrences sort by `(date, startTime ?? '00:00', marketId)` |
| HTTP | `PUT /market-days/:marketId/:date/items/:itemId/availability` → `{ soldOut: boolean }` |
| Vendor | live screen on its own route — active rows, *Épuisé* group, pre-live banner, poll while waiting, `concatMap` on the effect |
| Customer | dishes grey in place on the *Prochain marché* card; poll while live and visible |
| Ops | the stuck-subscription alert from `O11Y-PLAN.md` |

**Slice 2 — close.**

| | |
|---|---|
| Events | `MarketDayClosed`, `MarketDayReopened` |
| Aggregate | `_closed` in `apply`; `close` · `reopen` with idempotence guards; `MarketDayClosedError` from `setMenu`, `markItemAsSoldOut`, `markItemAsAvailable` |
| Read model | `closed` on the row; store gains `close` · `reopen` |
| Query | `FindNextMarketDay` keeps a closed day until `endTime`; the customer's list drops it |
| Vendor | **Close** at the foot of the live screen; the card renders *Terminé · Rouvrir* |

**Slice 3 — *en direct*.** The query split (`FindNextMarketDay` + a calendar-only
`FindUpcomingMarketDays`), occurrence assembly given one home, the editor narrowed to the next day.
Customer: the takeover hero — market, hours, street **and pitch** (plumbed through
`storefront-view-model.ts` for the first time) — rows with availability, the freshness label, and
*Marchés suivants* (already excludes the featured day — decision 33).

## Decisions

Settled by grilling. Do not re-litigate without a reason.

| # | Decision | Rationale |
|---|---|---|
| 1 | **Open is derived, close is an event.** Live = `inProgress && !closed`. No `MarketDayOpened` | The failure modes are asymmetric: a forgotten *open* tap kills the feature during the exact window it exists for, a forgotten *close* leaves today's behaviour. Close is also the trigger the later three-outcomes rating hangs off |
| 2 | **`MarketDayClosed` is an early `endTime`** — `notYetEnded` learns about it, ~~the day drops out of upcoming for vendor and customer~~ the day leaves the **customer's** view (revised by decision 10 — the vendor keeps it until `endTime` so it can be reopened), `inProgress` goes false, the storefront falls back to the normal page | One rule reused. Without it a vendor who sold out at 11h30 leaves a card reading *8h–13h · En cours* until 13h — worse than having no close at all. No bespoke *c'est terminé* screen: the next-market card already answers *when can I get this*. Two markets in one day works with no special case — closing the morning market promotes the evening one, which goes live on its own `startTime` |
| 3 | **Split the query.** `FindNextMarketDay(vendorId)` → one occurrence + dishes + availability + live/closed. `FindUpcomingMarketDays` sheds its menu join and becomes a pure calendar read | Live mode's state is day-scoped; joining sold-out across a 56-day horizon puts a third range read into a window join to serve one row. Days 2–5 already carry a menu list that is structurally always empty (decision 7 of `MENU-DU-JOUR-PLAN.md` leaves no UI to plan beyond the next market). **Contradicts that plan's decision 5** — menus rode on `MarketDayOccurrence` when a menu was the only day-scoped data. Also kills the frontend's `days().find(c => !c.absent)` scan at `next-menu-card.ts:38` |
| 4 | **No `FindCurrentMarketDay`** | Decision 1 makes *current* mean *next, after its `startTime`* — a second query would range over the same data and return the same row |
| 5 | **The menu editor narrows to the next market day** | It is only reachable from the dashboard card, so it always opened the next day in practice. A hand-typed URL for any other day falls into the existing *Ce marché n'est plus programmé* branch. Slice 4 declined a single-day GET because the editor prefilled from `items` on the upcoming payload; decision 3 removes that payload, and *plan later in time* becomes the trigger for `FindMarketDay(marketId, date)` |
| 6 | **Sold-out is reversible: `ItemMarkedAsAvailable` mirrors `ItemMarkedAsSoldOut`** — per-item, timestamped, not a whole-set replace | A vendor who taps the wrong row one-handed in the rain otherwise tells every approaching customer a dish is gone, fixable only by re-saving the menu — which nobody will discover. **Deliberately does not extend ADR 0047** (a market day's menu is set whole): the menu is a plan edited once in a sitting, availability is a stream of moments during service. A set loses the `time` the event already carries, and makes two taps on market wifi last-write-wins. Replay yields a per-dish availability timeline the waste-watch work can read. ~~`ItemAlreadySoldOutError` stays as an idempotence guard and gains a mirror~~ — revised by decision 36: the guards became silent no-ops and the error pair was deleted |
| 7 | **The undo does not sit next to the action.** Sold-out dishes leave the vendor's active list and collect in an *Épuisé* group at the bottom; restore is a tap inside that group | A toggle serves *found another tray* and causes *wrong row*. Marking stays one fast tap on a full-width row; the row visibly moving is the receipt, so a misfire is obvious instantly with no toast, timer or snackbar to build. The gradient is right — the active list shrinks as service goes on, the épuisés group grows. Rejected: undo toast (misses the later scenario), long-press/swipe (undiscoverable), confirm dialog (friction on the action that must be fastest). The **customer** list does not re-sort — sold-out greys in place, per the wireframe; shuffling rows under a reader's thumb is worse than a dead row |
| 8 | **The customer page polls the existing storefront endpoint every 60s while live and visible, and re-fetches on `visibilitychange` → visible.** *maj. il y a X min* counts from the last **successful** fetch. Repeated failures leave the page live with a stale timestamp | Sold-out marks that need a manual reload are worth nothing — the customer who matters is five minutes' walk away. Focus-refresh is the one that earns its keep: the real behaviour is open, walk, pocket the phone, pull it out at the stall. Rejected SSE/WebSocket — a long-lived connection and a projection→client bridge to save 30s for one pilot vendor. Reusing the storefront endpoint re-sends the carte each poll (a few kB of strings); split out a `/live` route when a real payload makes it measurable. The timestamp is the failure disclosure, not decoration — a covered market hall with bad 4G is the likely case, and a pulsing **EN DIRECT** over twenty-minute-old data is the lie the feature exists to avoid. Dropping the layout on a flaky tunnel would be a bigger lie than a stale menu; the customer can read *il y a 12 min* and judge |
| 9 | **Per-variant sold-out stays deferred.** A variant dish is one row on the vendor's live screen and greys whole on the customer's | The pilot vendor has no variant dishes, so it is a case that does not yet exist. ADR 0033's tolerant reader means adding `variantName` to `ItemMarkedAsSoldOut` later is additive and needs no version bump — so pre-adding it is scaffolding. Deferring also defers variant identity: `name` is the identity today and `ReviseItem` edits the whole set, so a per-variant mark could be orphaned by a rename; that lands with the ordering slice, which needs stable variant identity anyway. **Trigger: the first pilot vendor who puts a variant dish on a live menu** — the *popular format goes first* case is the normal one for such a dish, not an edge, so this flips from deferred to blocking the day it appears |
| 10 | **Two vendor routes, not one mode-switching screen.** `/dashboard/menus/:marketId/:date` stays the planner; live gets its own route. The dashboard card is the switch — ~~it links to the editor before `startTime` and to live during~~ revised by decision 27: it links to the **editor** while the day has no menu and to **live** once it does, from midnight. The live screen carries a discreet *Modifier le menu* link, and **Close** sits at the bottom, below the épuisés group | Same day, same dish list, an hour apart, opposite verbs — one screen flipping mode on a clock rather than on anything the vendor did is decision 7's footgun one rung up. The card is already a doorway (`MENU-DU-JOUR-PLAN.md` decision 7) and decision 3 gives it `live`, so the vendor never chooses. The editor must stay reachable during the market — *j'ai apporté une plaque de plus* is real, `setMenu` only guards past days, and adding a dish mid-market already clears sold-out for dropped items (`market-day.ts:24`). Close at the end of the page is the furthest point from the rows tapped all morning |
| 11 | **Close is reversible: `MarketDayClosed` / `MarketDayReopened`**, per-moment and timestamped like decision 6. `FindNextMarketDay` keeps a closed day until its `endTime` carrying `closed: true` — the vendor card renders *Terminé · Rouvrir*, the customer storefront reads closed as ended. `FindCustomerStorefrontHandler` drops that date+market from the *Prochains marchés* list it composes | A vendor who closes at 10h30 and then serves a straggler has otherwise ended their day publicly with no way back — and under decision 2 as first written, no query returned the day at all, so nothing could reach it. One query, two readings. The list filter matters: decision 3 made `FindUpcomingMarketDays` a pure calendar read with no market-day join, so without it the closed market still lists as *8h–13h* today and a customer walks over at 12h. No reopen guard — after `endTime` the day is unreachable through any UI, and a hand-crafted call would reopen something `notYetEnded` still drops |
| 12 | **Live requires a non-empty menu**: `inProgress && !closed && items.length > 0` (restated slice-by-slice in decision 26; the vendor's own gate differs — decision 27). No menu → today's behaviour, the normal storefront with the **En cours** badge | The likely pilot morning is a vendor who was loading the van at 6h and never planned. Without this the storefront replaces its hero with *on est au marché* over an empty *Au menu aujourd'hui* — a stall advertising no food, seen by every customer that morning, and the vendor who forgot to plan is the one who won't notice. Degrades both ways on its own: planning from the stall at 8h30 brings the takeover up on the next poll, so there is never a *go live* button; everything selling out keeps the menu non-empty so the page stays live with every row greyed, which is what a customer needs and the loudest hint to close. Accepted cost: a vendor can be at a market with no takeover and nothing tells them why — fixed on the vendor side, where the card during a live market with no menu reads *Vous êtes au marché · aucun plat au menu* rather than the planner's neutral prompt |
| 13 | **Two terms, not three. *En cours* = the market is running (schedule truth, `inProgress`, unchanged). *En direct* = the vendor is broadcasting today's menu (decision 12's trigger).** While live, *Prochains marchés* starts at the **next** market | Decision 12 made these genuinely two states — a live market with no menu is honestly *en cours* and not *en direct* — and *en direct* is French broadcast language, which is what the page is doing. The repeat rule in `MENU-DU-JOUR-PLAN.md` (a list silently starting at the second market reads as a bug) held for a modest card at the top; it does not survive a full-page takeover, where the day would appear twice — once as the hero, once as a card badged *En cours* beneath it. Merges with decision 11 into one rule: **the upcoming list excludes the day the page is currently featuring or has closed.** ~~Normal mode keeps repeating the promoted day, unchanged~~ — revised by decision 33: the exclusion is unconditional, so live mode inherits it. `NEXT_BEHAVIOURS.md`'s *open market day · close market day* is retired by decision 1 |
| 14 | **Live state extends `market-day-view` — one row per `(vendor, market, date)`, gaining `soldOutItemIds` and `closed`.** The store keeps intent methods (`markSoldOut` · `markAvailable` · `close` · `reopen`) so the projection stays a pass-through and the array append happens in SQL and in the in-memory twin. `setMenu` intersects `sold_out` with the new `itemIds`, mirroring `market-day.ts:24` | Post-decision-3 there is exactly one consumer of live state and it needs the menu in the same breath — nobody reads availability without the dishes it qualifies. Two rows keyed identically and always fetched together is a join paid on every poll to express a distinction no reader makes. Read models being disposable argues *for* the cheap shape: if it is wrong it costs a migration and a rebuild, which this codebase does routinely. The drift on that last rule is nearly harmless (a stale id isn't in `itemIds`, so the catalogue join drops it) except when the vendor re-adds the dish the same day — the flustered-mid-market case the feature exists for. **`menusFor(vendorId, from, to)` narrows to a point lookup and wants a name like `forDay`** — reversing decision 4 of `MENU-DU-JOUR-PLAN.md`, which had itself reversed an earlier point-lookup choice. Third decision live mode overturns |
| 14a | **The plan/outcome split is the waste-watch seam, not this one.** When the three-outcomes work lands it gets its own view — retrospective, keyed by dish across months, reading past days — built from the same `ItemMarkedAsSoldOut` / `MarketDayClosed` events | Conceptually the menu is a *plan* and availability is *what happened during service*, and that distinction is real. It just isn't a distinction any current reader makes: splitting now shapes a read model around a query that does not exist. The events are the durable record; the view that expresses the split gets built when something asks the question |
| 15 | **Occurrence assembly gets one home before either query is written** — expand recurrence → apply absences → join facts → apply temporal predicates | Decision 3 splits one handler into two, so the assembly currently inside `FindUpcomingMarketDaysHandler` would get two. That drift already bit once: `notYetEnded` and `parisWallClock` had to be hoisted out of the storefront handler in slice 5a. `MarketDayOccurrence` is a query DTO with no owner. **The structural invariant this all sits on:** *which day is next* and *is it running now* are time-driven, not event-driven — no event fires when a market starts or ends — which is why recurrence is expanded at query time and why a denormalised `next-market-day-view` (or a fully-projected storefront row) is not available: it would go stale at `endTime` with nothing to nudge it, and this system has no scheduler, only event-driven polling subscriptions |
| 16 | **All four commands require the day to be *today*** (and, per decision 29, not closed) — same shape as the existing `MarketDayInThePastError`, derivable from `_today` alone | *Require the day to be live* is not available: live needs `startTime`/`endTime` from the calendar, and slice 4 refused to read calendar state from the market-day write path off an eventually consistent read model. Closes `MENU-DU-JOUR-PLAN.md`'s known issue (marking next Saturday's dish sold out). Unreachable through the UI anyway — the live screen only exists during live mode — so it guards against a hand-crafted call. Deliberately unguarded: marking sold out at 6h, before the market opens; legal, harmless, arguably honest. **Known limit:** a market crossing midnight cannot work — taps after 00h would be rejected against the previous date. Pre-existing, since `endTime` is a `LocalTime` with no next-day concept, but live mode is the first feature that would notice |
| 17 | **The carte moves to its own `/carte` page permanently, not just while live.** `app.routes.ts` becomes a parent holding the resolver, with `''` → `StorefrontPage` and `'carte'` → `CartePage` as children. Ships **first — slice 0** (decision 18) | Deletes a conditional instead of adding one — the *demote the carte while live* rule existed only to stop two row-lists stacking, and a permanent split means live mode never has to know the carte exists. Two genuinely different jobs: home is *should I go*, carte is *what can they make*. Better SSR surface too — a real indexable page per vendor with dish names in it, and `storefront-metadata.ts` is already there to feed. One fetch serves both since children inherit the parent resolve; `RenderMode.Server` on `**` already covers the path. **The poll (decision 8) moves to the parent**, gated on live and running regardless of which child renders — on the page it would refetch-with-a-flicker or show stale prices on return from `/carte`. **The risk is discovery, not architecture:** the carte is the differentiator `MARKET_MIAM.md` builds the pitch on and now costs a tap, so it needs a visible *Notre carte* entry on the home page, not a footer link |
| 18 | **Slices, in order: (0) the `/carte` page, (1) sold-out end to end, (2) close, (3) *en direct* takeover** | `/carte` goes first on design-validation grounds, not rework: slice 1's whole customer-side deliverable is *how a sold-out dish reads on the storefront*, and judging that against a page we already intend to restructure means judging it twice. It is also the only slice with zero domain risk — routing and a resolver hoist, no events, no read model, no guards. The rework argument is weak and should not be leaned on: the poll is a route-provided service, so moving it from page to parent changes where it is provided, one line. Slice 1 has **no takeover**: sold-out greyed in place on the *Prochain marché* card that already exists is the whole customer-side value at no hero-redesign cost, and it is the honest test of whether vendors tap it at all — if they don't, slices 2 and 3 shouldn't be built. The query split (decision 3) waits for slice 3 at near-zero rework, because `dishesByDay` already range-scans the `MarketDayView` rows that decision 14 adds `soldOutItemIds` to — availability arrives in the read already being done. Slice 1 does need one non-obvious piece: **`inProgress` moves onto the occurrence.** It lives in `find-customer-storefront.handler.ts:51` on the customer DTO only, and the vendor's dashboard card needs it to switch from planner to live screen — decision 15's refactor arriving early, in its small form |
| 19 | **`PUT /market-days/:marketId/:date/items/:itemId/availability`, body `{ soldOut: boolean }`** — one idempotent route behind both commands; void response like every other command route | The menu route's whole-set `PUT` followed from *the menu is a set*, which decision 6 rejected for availability. Rejected `POST`+`DELETE /sold-out` (two routes, and `DELETE` reads as *delete the dish*) and a whole-set `PUT` (re-imports the last-write-wins problem). **Knowingly breaks the house one-route-one-command style**: a vendor's phone retrying on bad market signal must be safe, and `{soldOut: true}` twice is, where `POST` twice raises `ItemAlreadySoldOutError` and reads to the UI as a failure |
| 20 | **Accessibility ships in slice 1, not a polish pass.** `aria-live="polite"` on the **dish list only**; availability is text and never colour (drop `DISPONIBLE` with `BIENTÔT ÉPUISÉ` — the default state needs no badge); a sold-out row stays tappable; the pulse dot is `aria-hidden` and its animation gated on `prefers-reduced-motion`. On the vendor side, **focus moves deliberately when a tapped row leaves the active list**, and the move is announced | The page mutates with no user action and the change is a dish becoming unavailable — the highest-stakes silent mutation on it. Scoping the live region to the section rather than the list makes *maj. il y a X min* re-announce every minute forever, which turns the feature into one people switch off. Decision 7's row-leaves-the-list is the sharp edge: it destroys the focused element, so a vendor on a keyboard or switch control loses their place on every tap and the épuisés group becomes a trap. Cheap now, expensive to retrofit |
| 21 | **All liveness stays server-side; the client only ever re-asks.** The customer frontend gets `Clock` from `@market-miam/common` as an Angular provider, and *maj. il y a X min* is a wall-clock delta `now − lastSuccessfulFetch` | Letting the browser flip into live mode at `now >= startTime` computes liveness in the *browser's* timezone — a customer checking from London sees the Lyon market closed for another hour. Slice 4 paid for that lesson once with `TZ=Europe/Paris` on the API service, and the customer frontend has no timezone handling at all (ISO strings split against a lookup table, no `Intl`, no `registerLocaleData`). A tick counter for the label breaks where it matters: a phone in a pocket suspends timers, so a tab backgrounded twenty minutes would read *il y a 2 min* — the exact lie decision 8 exists to prevent. Reusing `Clock` keeps ADR 0013's *now enters in exactly one way* true repo-wide instead of adding a second time abstraction for one label, and makes the label testable by fixing the clock rather than faking timers |
| 22 | **`concatMap` on the availability effect**, not the `switchMap` the menu save uses | `market-day.effects.ts:37` uses `switchMap`, which *cancels* the in-flight request when the next arrives — correct for one whole-set save per screen, silently fatal for rapid taps: three dishes in five seconds and only the last survives, with no error shown while the vendor believes all three landed. `concatMap` queues instead, and because each request completes before the next loads the aggregate, the `ConcurrencyError`→409 from concurrent appends to one stream cannot arise from a single client. Decision 19 pays off here: per-item routes give per-item failure, so a tap that fails on bad signal reverts its own row visibly while the others stand — a whole-set `PUT` would fail them together and leave the UI guessing. The optimistic patch means the queue drains behind the UI, so a slow request never blocks the vendor. **Named limit, not solved: two devices still conflict** — a phone and a tablet at one stall can 409 each other. Retry-on-409 is the fix if it ever appears; building it now is infrastructure for a scenario the pilot cannot produce |
| 23 | **A second demo vendor that is always live**, scheduled `00:00–23:59` every weekday, with **menus scripted a year ahead** by a one-off `PUT` loop. That is a better demo than a static badge, and the one moment decision 8's polling delay becomes a selling point. The website keeps a screenshot for the épuisé state |
| 24 | **No new spans or span attributes. The deferred stuck-subscription alert moves from evidence-gated into slice 1** | Every failure here is silent — nothing throws when a projection stalls or a poll dies, and the page serves stale data under a confident *En direct*, converting a neutral page into a misleading one. | 26 | **The live predicate is slice-monotone**: slice 1 is `inProgress && items.length > 0`, slice 2 adds `&& !closed`, slice 3 changes rendering only. | 27 | **The vendor's gate is `today && items.length > 0`, not the customer's.** Before `startTime` the live screen shows *« Vos clients verront ce menu à partir de 8h00 »* — a stated boundary, **not a countdown** — and polls (decision 8's mechanism, gated on waiting) until it goes live, then stops | Decision 16 deliberately permits marking sold out at 6h, which the customer's `inProgress` gate makes unreachable — a guard allowing something no screen can perform. There is no ops surface (`admin-api`/`admin-frontend` are empty and `NEXT_BEHAVIOURS.md` gates ops transport on one existing), so this is a psql session, not a feature. **No success threshold, deliberately**: with one pilot vendor the denominator is single digits, so a ratio is not evidence — the log says *whether*, and only asking the vendor says *why*. A number invented now would later be quoted as if it meant something |
| 29 | **Close is a phase boundary on the aggregate, not a display flag.** `_closed` enters `apply` (`MarketDayClosed` → true, `MarketDayReopened` → false), and `markItemAsSoldOut`, `markItemAsAvailable` **and `setMenu`** all throw `MarketDayClosedError` (a `DomainError` → 400) once closed. Close and reopen carry their own idempotence guards, mirroring `ItemAlreadySoldOutError` | Before close, availability events; after it, outcome events. *It's gone right now* and *it sold out that day* are two different claims about one dish that would otherwise both be expressible at the same moment, sharing a word and meaning different things — the later three-outcomes rating takes over at close, so the service-phase commands must stop. This also gives `closed` a real invariant instead of leaving it write-only state the aggregate emits and never reads. **`setMenu` is included for a sharper reason:** it *clears sold-out* at `market-day.ts:24`, so editing a closed day would wipe the service-phase history the ratings are about to be derived from, and a dish removed after rating leaves the outcome dangling against a menu that no longer claims it. `MENU-DU-JOUR-PLAN.md` slice 4 predicted this guard — waste-watch "will want *no editing a day with recorded outcomes* rather than *no past days*" — and closing is its earlier, cheaper form, available before outcomes exist |
| 30 | **`MarketDayReopened` clears recorded outcomes.** Nothing to build — ratings do not exist — but it is the constraint the rating slice inherits | Vendor closes at 11h30, rates the day, a straggler turns up, they reopen and sell more: the earlier ratings are now stale. `MarketDayMenuSet` clearing sold-out at `market-day.ts:24` is the precedent for the shape. Written down here or the rating slice rediscovers it |
| 31 | **The small ones, stated so they are not rediscovered:** `apply` for `ItemMarkedAsAvailable` removes the id from `_soldOut`; sold-out **survives** close → reopen; erasure needs no change | Mirrors the `MarketDayMenuSet` filter at `market-day.ts:24`. Closing says *we've packed up*, not *the bourguignon came back*. The three new event types carry `itemId`, `marketId`, `date` and a time — no PII, so `VendorErasure` still does not rebuild this read model, exactly as `MENU-DU-JOUR-PLAN.md` recorded for the menu event |
| 32 | **No forward test plan — it is built with outside-in TDD.** Two notes only: **(a)** new store methods join `market-day-views.contract.ts`, not just the adapter the driving test touched; **(b)** the poll's *should we be polling?* gate is an extractable predicate, separate from the interval | A test table written ahead is the tests written twice, and the second version is the wrong one — `MENU-DU-JOUR-PLAN.md`'s tables are records of what shipped, not plans. The contract suite is the one thing TDD will not drive you to: `MarketDayViewStore` is abstract, so a *missing* Postgres method is a compile error, but a method that exists and behaves differently passes every driving test against the in-memory twin — decision 14's intersection rule is exactly that shape. The gate/timer split is a design decision wearing a test costume: it decides whether the poll can be driven at all without dragging fake timers into a suite that has none, and the interval firing is not a bug that will happen, where the gate being wrong (polling a dead page forever, or never starting) is |
| 33 | **The list always drops the day featured above it, and is titled *Marchés suivants*** — normal mode is *Prochain marché* + *Marchés suivants*, live mode is the hero + the same list. Shipped in slice 0 | Decision 13 made the exclusion conditional on live mode, leaving the normal page showing one market twice within a screen — identical cards, on a day with no menu planned (`tmp/too-much.png`). The repeat rule it inherited from `MENU-DU-JOUR-PLAN.md` (*a list silently starting at the second market reads as a bug*) was written when a full carte sat between the two cards and the featured card carried a menu; slice 0 turned the carte into one button and removed both premises. The heading now carries the meaning, so nothing reads as a missing first entry. Unconditional also deletes the branch slice 3 would have needed: the list is *what comes after the card above it*, live or not. Five distinct days shown either way — one promoted, four listed, `MAX_UPCOMING` untouched |
| 34 | **The model's word is *item*, repo-wide.** `dishes` DTO fields, `Dish*` types and dish-named files renamed to item across API, frontends and tests; the slice 1 route reads `items/:itemId`, not `dishes/:itemId` | The domain always said item (`ItemId`, `ItemMarkedAsSoldOut`, `AddItemToCatalogue`); *dish* leaked in through the read DTOs and frontends, and the availability route as first written carried both words in one URL. The vendor's real word is French — *plat*, in every label, untouched — so the English pick is a code concern only, and item is the one that survives non-dish catalogue entries (bocaux, sauces, desserts). Two deliberate keeps: the Cloudinary `dishes/` folder (existing uploads live under it; splitting the media library serves no reader) and history — events, ADRs and archived plans read as written |
| 35 | **Availability commands carry no clock time — the server stamps it.** `MarkItemAsSoldOut` loses its `time` field; the handler reads `Clock.now()` once and writes the event's `time` via `parisWallClock`; `MarkItemAsAvailable` is born without the field. The **event** keeps `time` in its payload | Decision 19's body is `{ soldOut: boolean }`, so no client time exists to carry — the field was a hole every caller had to fill from the server clock anyway, and the one door a wrong clock (a phone's, a browser's timezone) could enter the write side through. Extends decision 21 into the command shape: *now* enters once, via `Clock` (ADR 0013), and the stamp comes from the same `Clock` that feeds the aggregate's `_today` guard, so a device clock can never contradict the guard. The store envelope's `timestamp` is no substitute — it is `Date.now()` in the adapter, not `Clock`, and epoch-ms would push timezone math onto every reader where *sold out at 11h42* is the domain fact (decision 6). Offline capture would reintroduce a client-observed time as request data — a decision for the day offline exists, not scaffolding now |
| 36 | **Re-stating availability is a no-op, not an error.** `markItemAsSoldOut` on an already-sold-out item (and its mirror) returns without raising; `ItemAlreadySoldOutError` and `ItemAlreadyAvailableError` are deleted | The guard's real job is to not append a duplicate event — a second `ItemMarkedAsSoldOut` would corrupt the per-item timeline waste-watch reads — and a silent return does that job completely. The throw was the domain's outlier: `setMenu` with an unchanged menu and retiring twice are already no-ops, and decision 19's idempotent route would have obligated the controller to catch the pair and call it 200 — two layers disagreeing about one command. What stays an error is a *wrong* claim (`ItemNotPlannedError`, `MarketDayNotTodayError`), not a *redundant* one. If a caller ever needs to distinguish no-op from append, that is a response-shape decision for that day |

## ADR

[0049 — A market day opens by the clock, closes by hand](adr/0049-market-day-opens-by-the-clock-closes-by-hand.md),
for decision 1. An asymmetric lifecycle in an event-sourced domain is exactly what a later
contributor "corrects", and the reason — asymmetric failure modes, not oversight — is invisible
from the code.

Considered and skipped, because read models, routes and queries here are cheap to reverse and the
rationale above is enough: the query split (3), live state on the menu row (14), the idempotent
availability route (19), server-only liveness (21).

## Named limits

Accepted deliberately; none block a slice.

- **No presence guarantee.** *On est au marché* is inferred from the schedule, so a vendor whose
  van broke down reads as trading until `endTime` or until they close (ADR 0049).
- **A market crossing midnight cannot work** — decision 16. Pre-existing: `endTime` is a
  `LocalTime` with no next-day concept.
- **Two devices can 409 each other** — decision 22. One vendor, one phone is the real case.
- **Overlapping markets.** The schedule model permits two markets whose hours overlap; one stall
  cannot be at both, and first-by-start-time wins (decision 25). A data-entry mistake, not a rule
  to write.
- **Per-variant sold-out** — decision 9, with its trigger recorded there.
