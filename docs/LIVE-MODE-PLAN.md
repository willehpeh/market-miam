# Live mode — plan

A market day the vendor is trading *right now*: the storefront leads with the market it is
standing in, the day's menu carries per-dish availability, and the vendor closes the day when
they pack up. Wireframe: `tmp/live-mode.png` (its logo and *bientôt épuisé* tag are not the
design).

Slice 0 shipped. Slice 1's backend is built through HTTP — both availability events, the
today-guard, `soldOutItemIds` on the read model and both query payloads, `inProgress` and
`today` (decision 42) on the occurrence, the sort fix, and the idempotent availability route —
and the vendor side is shipped: the doorway card (decisions 41–43) and the live screen with
its rows, épuisé group, pre-live banner, waiting poll and *En direct* receipt. The customer
side is shipped too: sold-out greys in place on the *Prochain marché* card, and a
route-provided feed polls while broadcasting and re-asks on the tab becoming visible
(decisions 7, 8, 17, 20, 26). The ops alert is shipped too — the span as designed, with
paging through `GET /api/health` and an external monitor, the free tier having no trigger
slot (`O11Y-PLAN.md` step 5). **Slice 1 is complete.**

**Slice 2's backend is complete**, built through HTTP: both events, `close` and `reopen` with
their *today*, no-op and ended guards, `_closed` in `apply`, decision 29's guards on `setMenu`
and both availability commands, `closed` on the read model and on the occurrence, the customer
list dropping a closed day, the idempotent `PUT …/closed`, and `GET /market-days/:marketId/:date`
behind `FindMarketDay` (decision 50). **Slice 2 is complete.** The live screen carries close, the
closed state, reopen, the inert rows and decision 10's editor link; the foot's one verb flips
at `startTime` (decision 52); the card carries the call-off for any today and the closed state
ahead of the menu (decisions 51, 55); the editor carries the closed state alone (decision 53).
**Next is the vendor frontend's `FindMarketDay` read** (decisions 58-60), then slice 2b or slice 3. **Slice 2b is still
not startable as written**, but on one count rather than two: the French copy for the two
judgments is open. The rating capture window is settled — decision 50 dissolved it.

## Shape

What gets built, in order. Why is in the decisions below.

**Slice 0 — `/carte`. Done.** `app.routes.ts` is a componentless parent holding
`storefrontResolver`, children `''` → `StorefrontPage` and `'carte'` → `CartePage`; a *Notre carte*
row on the home page. Three things the plan did not call:

- **The metadata card moved from `StorefrontPage.ngOnInit` into the resolver.** It was the only
  call site, so `/carte` would have shipped with the fallback `<title>`; in the resolver it covers
  every route under the resolve and the lifecycle hook goes away. Both pages get the same card —
  a per-page title is skipped, duplicate across two pages of one site, not worth a branch at one
  vendor.
- **The carte renders `DishCard`, and `DishRow` is deleted.** Rows existed only to stop the carte
  and the day's menu competing on size on one page; separate pages ended that. Photo-less dishes
  get a `bg-canvas` panel with the fork-and-knife, on the card and in the sheet.
- **`app.routes.spec.ts` fakes `HttpBackend` rather than using `HttpTestingController`** — a
  resolver runs inside the navigation, so flushing by hand races the router. It also counts
  requests, which is what proves one fetch serves both children.

**Slice 1 — sold-out, end to end. Shipped whole.** Migration `0014` and the Postgres availability SQL were written in an environment with no Docker; the container suite has since been run and passes, so the adapter is verified, not just contract-covered.

| | |
|---|---|
| Event | `ItemMarkedAsAvailable`, mirroring `ItemMarkedAsSoldOut` |
| Aggregate | `markItemAsAvailable`; both guarded to *today* |
| Read model | `market-day-view` gains `soldOutItemIds`; store gains `markSoldOut` · `markAvailable`; `setMenu` intersects `sold_out` with the new `itemIds` |
| Query | availability joins onto the occurrence; `inProgress` moves onto the occurrence; the occurrence gains `today` (decision 42); occurrences sort by `(date, startTime ?? '00:00', marketId)` |

| Customer | dishes grey in place on the *Prochain marché* card; poll while live and visible |
| Ops | the stuck-subscription alert from `O11Y-PLAN.md` |

**Slice 2 — close.**

| | |
|---|---|
| Events | `MarketDayClosed`, `MarketDayReopened` |
| Aggregate | `_closed` in `apply`; `close` · `reopen` with idempotence guards; `MarketDayClosedError` from `setMenu`, `markItemAsSoldOut`, `markItemAsAvailable` |
| Read model | `closed` on the row; store gains `close` · `reopen` |
| Query | the vendor's occurrence carries `closed`; the customer's list drops a closed day; `FindMarketDay(marketId, date)` reads one day with no window at all (decision 50) |
| HTTP | `PUT /market-days/:marketId/:date/closed` → `{ closed: boolean }` (decision 44); `GET /market-days/:marketId/:date` → the occurrence, 404 when the schedule does not cover it |
| Vendor | **Fermer le stand** at the foot of the live screen, no confirm dialog; once closed the screen goes inert — rows untappable **as availability controls but still rows** (decisions 38, 48), *Modifier le menu* hidden, **Rouvrir le stand** where it stood; the card renders *Stand fermé · Rouvrir*; the pre-live screen gains *Je ne peux pas venir aujourd'hui* (decisions 40, 45), and so does the editor's foot on a day that is today, with the card reading `closed` before `items` (decision 51). Decision 10's discreet *Modifier le menu* link on the live screen was never built in slice 1 — it lands here, and closing is what hides it |

Four things the plan did not call, landing across slice 2's backend:

- **`MarketDays.save` lost its `MarketDayId` argument.** The aggregate says its own stream id,
  so all four market-day handlers now match the `save(aggregate, vendorId)` shape every other
  handler in the repo already used — and no handler can save one day under another's stream.
- **The `vendorId` metadata stamp is asserted once, at the seam.** Fourteen use-case specs each
  re-checked it through five structurally identical repositories; they now defer to
  `vendor-scoped-events.spec.ts`, with a `no-restricted-syntax` rule in the package's
  `eslint.config.mjs` making `VendorScopedEvents` the only caller of `append`. A second door —
  a context whose events are not vendor-scoped — is one `ignores` entry and a reworded message.
- **The read model's `close` upserts, where the availability marks do not.** A mark for an
  unplanned day is only ever a replay artefact, so it lands on no row; a close for one is
  decision 40's *Je ne peux pas venir aujourd'hui*, and dropping it would leave the customer
  reading a market the vendor had already called off. `reopen` keeps the marks' shape — there
  is nothing to reopen without a close.
- **`MarketDays` reads the vendor's calendar** so the aggregate is constituted with the day's
  hours (decision 50). `Calendar.apply` had never handled `MarketScheduleAmended`, which was
  harmless while it only tracked `marketId` and is not once it answers about hours.

Four more the plan did not call, landing with slice 2's live screen:

- **The editor's exits were both hard-wired to the dashboard**, so a vendor who tapped
  *Modifier le menu* mid-market was thrown out of the day to save one dish. The card's own gate
  is now one predicate — `hasLiveScreen(day)` in `live-status.ts`, decision 27's `today &&
  itemIds.length > 0` — read by the card, by `awaitingStart`, and by both of the editor's exits,
  so the doorway and the way back cannot drift apart. `SetMarketDayMenuSuccess` reads it after
  its own patch (reducers run before effects), which is why saving today's first menu lands on
  the live screen rather than where the vendor came from.
- **The closed banner outranks the live one.** Decision 38 took the confirm dialog away on
  purpose, which leaves the banner as the only thing telling a vendor a mistap just took them
  out of every customer's list — so *Stand fermé* is the loud state and *En direct* the quiet
  one, not the other way round. It carries the consequence as a subline, *Vos clients ne voient
  plus ce marché.* — copy decision 45 did not settle.
- **Decision 48's *inert* got a visual form**: closed rows sink onto the canvas and lose their
  border, keeping their text at full strength. Dimming was rejected twice over — the base layer's
  `disabled:opacity-50` is unreadable in market sun, and the day's menu is still what the vendor
  is reading. The raised card is what says *tappable*, so that is what goes.
- **`.quiet` became a design-system utility**, out of `add-item.ts` where it dressed *Annuler*.
  *Fermer le stand* is the second neutral outline control in the app: not the brand colour, which
  belongs to *En direct* and would out-shout the dishes, and not the danger colour, which
  overclaims a state decision 38 calls more reversible than sold-out.

**Slice 2b — outcomes (decision 47).** Between close and the takeover: the three outcomes per
item per market day that `MARKET_MIAM.md` calls post-market tracking.

| | |
|---|---|
| Event | `ItemOutcomeRecorded` — `itemId`, one of `sold_out` · `did_well` · `did_not_do_well`, server-stamped time (decision 35) |
| Aggregate | outcomes enter `apply`; `recordItemOutcome` guarded to a **closed** day (decision 29's phase boundary) and to *today* (decision 16); `MarketDayReopened` clears them (decision 30) |
| Read model | outcomes ride `market-day-view` beside `soldOutItemIds` — decision 14's one row, same reader, same breath. The retrospective cross-month view stays deferred (decision 14a) |
| HTTP | per-item and idempotent, availability's shape (decisions 19, 44) |
| Vendor | the closed screen's rating mode (decision 48); sold-out prefilled from the service log and overridable, so a vendor who marked four dishes épuisé judges only the rest (decision 49) |

**Slice 3 — *en direct*.** The query split (`FindNextMarketDay` + a calendar-only
`FindUpcomingMarketDays`), occurrence assembly given one home, the editor narrowed to the next day.
Customer: the takeover hero — market, hours, street **and pitch** (plumbed through
`storefront-view-model.ts` for the first time) — rows with availability, the freshness label, and
*Marchés suivants* (already excludes the featured day — decision 33).

## Decisions

Settled by grilling. Do not re-litigate without a reason.

| # | Decision | Rationale |
|---|---|---|
| 1 | **Open is derived, close is an event.** Live = `inProgress && !closed`. No `MarketDayOpened` | The failure modes are asymmetric: a forgotten *open* tap kills the feature during the exact window it exists for, a forgotten *close* leaves today's behaviour. Close is also the trigger the later three-outcomes rating hangs off |
| 2 | **`MarketDayClosed` is an early `endTime`** — `notYetEnded` learns about it, ~~the day drops out of upcoming for vendor and customer~~ the day leaves the **customer's** view (revised by decision 10 — the vendor keeps it until `endTime` so it can be reopened), `inProgress` goes false, the storefront falls back to the normal page | One rule reused. Without it a vendor who sold out at 11h30 leaves a card reading *8h–13h · En cours* until 13h — worse than having no close at all. No bespoke *c'est terminé* screen: the next-market card already answers *when can I get this*. Two markets in one day works with no special case — closing the morning market promotes the evening one, which goes live on its own `startTime` |
| 3 | **Split the query.** `FindNextMarketDay(vendorId)` → one occurrence + dishes + availability + live/closed. `FindUpcomingMarketDays` sheds its menu join and becomes a pure calendar read | Live mode's state is day-scoped; joining sold-out across a 56-day horizon puts a third range read into a window join to serve one row. Days 2–5 already carry a menu list that is structurally always empty (decision 7 of `MENU-DU-JOUR-PLAN.md` leaves no UI to plan beyond the next market). **Contradicts that plan's decision 5** — menus rode on `MarketDayOccurrence` when a menu was the only day-scoped data. Also kills the frontend's `days().find(c => !c.absent)` scan at `next-menu-card.ts:38` |
| 4 | **No `FindCurrentMarketDay`** | Decision 1 makes *current* mean *next, after its `startTime`* — a second query would range over the same data and return the same row |
| 5 | **The menu editor narrows to the next market day** | It is only reachable from the dashboard card, so it always opened the next day in practice. A hand-typed URL for any other day falls into the existing *Ce marché n'est plus programmé* branch. Slice 4 declined a single-day GET because the editor prefilled from `items` on the upcoming payload; decision 3 removes that payload, and *plan later in time* becomes the trigger for `FindMarketDay(marketId, date)` |
| 6 | **Sold-out is reversible: `ItemMarkedAsAvailable` mirrors `ItemMarkedAsSoldOut`** — per-item, timestamped, not a whole-set replace | A vendor who taps the wrong row one-handed in the rain otherwise tells every approaching customer a dish is gone, fixable only by re-saving the menu — which nobody will discover. **Deliberately does not extend ADR 0047** (a market day's menu is set whole): the menu is a plan edited once in a sitting, availability is a stream of moments during service. A set loses the `time` the event already carries, and makes two taps on market wifi last-write-wins. Replay yields a per-dish availability timeline the waste-watch work can read. ~~`ItemAlreadySoldOutError` stays as an idempotence guard and gains a mirror~~ — revised by decision 36: the guards became silent no-ops and the error pair was deleted |
| 7 | **The undo does not sit next to the action.** Sold-out dishes leave the vendor's active list and collect in an *Épuisé* group at the bottom; restore is a tap inside that group | A toggle serves *found another tray* and causes *wrong row*. Marking stays one fast tap on a full-width row; the row visibly moving is the receipt, so a misfire is obvious instantly with no toast, timer or snackbar to build. The gradient is right — the active list shrinks as service goes on, the épuisés group grows. Rejected: undo toast (misses the later scenario), long-press/swipe (undiscoverable), confirm dialog (friction on the action that must be fastest). The **customer** list does not re-sort — sold-out greys in place, per the wireframe; shuffling rows under a reader's thumb is worse than a dead row |
| 8 | **The customer page polls the existing storefront endpoint every 60s while live and visible, and re-fetches on `visibilitychange` → visible.** *maj. il y a X min* counts from the last **successful** fetch. Repeated failures leave the page live with a stale timestamp | Sold-out marks that need a manual reload are worth nothing — the customer who matters is five minutes' walk away. Focus-refresh is the one that earns its keep: the real behaviour is open, walk, pocket the phone, pull it out at the stall. Rejected SSE/WebSocket — a long-lived connection and a projection→client bridge to save 30s for one pilot vendor. Reusing the storefront endpoint re-sends the carte each poll (a few kB of strings); split out a `/live` route when a real payload makes it measurable. The timestamp is the failure disclosure, not decoration — a covered market hall with bad 4G is the likely case, and a pulsing **EN DIRECT** over twenty-minute-old data is the lie the feature exists to avoid. Dropping the layout on a flaky tunnel would be a bigger lie than a stale menu; the customer can read *il y a 12 min* and judge |
| 9 | **Per-variant sold-out stays deferred.** A variant dish is one row on the vendor's live screen and greys whole on the customer's | The pilot vendor has no variant dishes, so it is a case that does not yet exist. ADR 0033's tolerant reader means adding `variantName` to `ItemMarkedAsSoldOut` later is additive and needs no version bump — so pre-adding it is scaffolding. Deferring also defers variant identity: `name` is the identity today and `ReviseItem` edits the whole set, so a per-variant mark could be orphaned by a rename; that lands with the ordering slice, which needs stable variant identity anyway. **Trigger: the first pilot vendor who puts a variant dish on a live menu** — the *popular format goes first* case is the normal one for such a dish, not an edge, so this flips from deferred to blocking the day it appears |
| 10 | **Two vendor routes, not one mode-switching screen.** `/dashboard/menus/:marketId/:date` stays the planner; live gets its own route. The dashboard card is the switch — ~~it links to the editor before `startTime` and to live during~~ revised by decision 27: it links to the **editor** while the day has no menu and to **live** once it does, from midnight. The live screen carries a discreet *Modifier le menu* link, and **Close** sits at the bottom, below the épuisés group | Same day, same dish list, an hour apart, opposite verbs — one screen flipping mode on a clock rather than on anything the vendor did is decision 7's footgun one rung up. The card is already a doorway (`MENU-DU-JOUR-PLAN.md` decision 7) and decision 3 gives it `live`, so the vendor never chooses. The editor must stay reachable during the market — *j'ai apporté une plaque de plus* is real, `setMenu` only guards past days, and adding a dish mid-market already clears sold-out for dropped items (`market-day.ts:24`). Close at the end of the page is the furthest point from the rows tapped all morning |
| 11 | **Close is reversible: `MarketDayClosed` / `MarketDayReopened`**, per-moment and timestamped like decision 6. ~~`FindNextMarketDay` keeps a closed day until its `endTime` carrying `closed: true`~~ — revised by decision 50: the day is readable forever through `FindMarketDay`, and `endTime` limits reopening rather than visibility. The vendor's list keeps a closed day until its `endTime` carrying `closed: true` — the vendor card renders ~~*Terminé · Rouvrir*~~ *Stand fermé · Rouvrir* (decision 45), the customer storefront reads closed as ended. `FindCustomerStorefrontHandler` drops that date+market from the *Prochains marchés* list it composes | A vendor who closes at 10h30 and then serves a straggler has otherwise ended their day publicly with no way back — and under decision 2 as first written, no query returned the day at all, so nothing could reach it. One query, two readings. The list filter matters: decision 3 made `FindUpcomingMarketDays` a pure calendar read with no market-day join, so without it the closed market still lists as *8h–13h* today and a customer walks over at 12h. ~~No reopen guard — after `endTime` the day is unreachable through any UI, and a hand-crafted call would reopen something `notYetEnded` still drops~~ — that unreachability was the whole enforcement, and decision 50 removes it, so the guard became real |
| 12 | **Live requires a non-empty menu**: `inProgress && !closed && items.length > 0` (restated slice-by-slice in decision 26; the vendor's own gate differs — decision 27). No menu → today's behaviour, the normal storefront with the **En cours** badge | The likely pilot morning is a vendor who was loading the van at 6h and never planned. Without this the storefront replaces its hero with *on est au marché* over an empty *Au menu aujourd'hui* — a stall advertising no food, seen by every customer that morning, and the vendor who forgot to plan is the one who won't notice. Degrades both ways on its own: planning from the stall at 8h30 brings the takeover up on the next poll, so there is never a *go live* button; everything selling out keeps the menu non-empty so the page stays live with every row greyed, which is what a customer needs and the loudest hint to close. | 13 | **Two terms, not three. *En cours* = the market is running (schedule truth, `inProgress`, unchanged). *En direct* = the vendor is broadcasting today's menu (decision 12's trigger).** While live, *Prochains marchés* starts at the **next** market | Decision 12 made these genuinely two states — a live market with no menu is honestly *en cours* and not *en direct* — and *en direct* is French broadcast language, which is what the page is doing. The repeat rule in `MENU-DU-JOUR-PLAN.md` (a list silently starting at the second market reads as a bug) held for a modest card at the top; it does not survive a full-page takeover, where the day would appear twice — once as the hero, once as a card badged *En cours* beneath it. Merges with decision 11 into one rule: **the upcoming list excludes the day the page is currently featuring or has closed.** ~~Normal mode keeps repeating the promoted day, unchanged~~ — revised by decision 33: the exclusion is unconditional, so live mode inherits it. `NEXT_BEHAVIOURS.md`'s *open market day · close market day* is retired by decision 1 |
| 14 | **Live state extends `market-day-view` — one row per `(vendor, market, date)`, gaining `soldOutItemIds` and `closed`.** The store keeps intent methods (`markSoldOut` · `markAvailable` · `close` · `reopen`) so the projection stays a pass-through and the array append happens in SQL and in the in-memory twin. `setMenu` intersects `sold_out` with the new `itemIds`, mirroring `market-day.ts:24` | Post-decision-3 there is exactly one consumer of live state and it needs the menu in the same breath — nobody reads availability without the dishes it qualifies. Two rows keyed identically and always fetched together is a join paid on every poll to express a distinction no reader makes. Read models being disposable argues *for* the cheap shape: if it is wrong it costs a migration and a rebuild, which this codebase does routinely. The drift on that last rule is nearly harmless (a stale id isn't in `itemIds`, so the catalogue join drops it) except when the vendor re-adds the dish the same day — the flustered-mid-market case the feature exists for. **`menusFor(vendorId, from, to)` narrows to a point lookup and wants a name like `forDay`** — reversing decision 4 of `MENU-DU-JOUR-PLAN.md`, which had itself reversed an earlier point-lookup choice. Third decision live mode overturns |
| 14a | **The plan/outcome split is the waste-watch seam, not this one.** When the three-outcomes work lands it gets its own view — retrospective, keyed by dish across months, reading past days — built from the same `ItemMarkedAsSoldOut` / `MarketDayClosed` events | Conceptually the menu is a *plan* and availability is *what happened during service*, and that distinction is real. The events are the durable record; the view that expresses the split gets built when something asks the question |
| 15 | **Occurrence assembly gets one home before either query is written** — expand recurrence → apply absences → join facts → apply temporal predicates | Decision 3 splits one handler into two, so the assembly currently inside `FindUpcomingMarketDaysHandler` would get two. Unreachable through the UI anyway — the live screen only exists during live mode — so it guards against a hand-crafted call. Deliberately unguarded: marking sold out at 6h, before the market opens; legal, harmless, arguably honest. **Known limit:** a market crossing midnight cannot work — taps after 00h would be rejected against the previous date. Pre-existing, since `endTime` is a `LocalTime` with no next-day concept, but live mode is the first feature that would notice |

Ships **first — slice 0** (decision 18) | Deletes a conditional instead of adding one — the *demote the carte while live* rule existed only to stop two row-lists stacking, and a permanent split means live mode never has to know the carte exists. ## ADR

[0049 — A market day opens by the clock, closes by hand](adr/0049-market-day-opens-by-the-clock-closes-by-hand.md),
for decision 1. An asymmetric lifecycle in an event-sourced domain is exactly what a later
contributor "corrects", and the reason — asymmetric failure modes, not oversight — is invisible
from the code.

[0051 — A market day is constituted with its market's hours](adr/0051-market-day-constituted-with-its-markets-hours.md),
for decision 50. The repository reading a sibling aggregate and constructing the day with its
hours is a third shape for a cross-aggregate fact, beside the handler passing one (`setMenu`'s
`Menu`) and ADR 0031's domain service — and 0031 says in as many words that passed-in aggregates
are the reach a service exists to own. The rule for telling the three apart lived nowhere.

Considered and skipped, because read models, routes and queries here are cheap to reverse and the
rationale above is enough: the query split (3), live state on the menu row (14), the idempotent
availability and close routes (19, 44), server-only liveness (21). Weighed again once 50 and 56
had shipped, since that list was written before either existed: the one phase (56) stays here —
the rule a contributor would undo, clock truth held apart from `closed` and `absent`, is in the
type's own comment where the decision put it — and the *item* rename (34) is 0020's shape exactly
and would cite it for the same reason, which is thin. **Still a candidate: the no-op rule (36)**,
which deleted two error types and governs every command in the repo, a scope written nowhere.

## Named limits

Accepted deliberately; none block a slice.

- **No presence guarantee.** *On est au marché* is inferred from the schedule, so a vendor whose
  van broke down reads as trading until `endTime` or until they close (ADR 0049). Re-examined and
  kept: a gating `MarketDayOpened` fails false-negative (feature silently off all morning, on the
  most load-bearing request of the day, from the worst network moment), needs a reminder — and so
  a scheduler this system deliberately lacks (decision 15) — and breaks the always-live demo
  vendor (decision 23). If presence-doubt ever proves real, the recorded shape is an **additive**
  open — never gating, `(inProgress || openedToday)`, upgrading the hero copy to the presence
  claim it currently cannot make. **Trigger: a customer or the vendor reports the page claiming
  presence that wasn't there, or the vendor asks how to signal they're running late.**
- **A market crossing midnight cannot work** — decision 16. Pre-existing: `endTime` is a
  `LocalTime` with no next-day concept.
- **Two devices can 409 each other** — decision 22. One vendor, one phone is the real case.
- **Overlapping markets.** The schedule model permits two markets whose hours overlap; one stall
  cannot be at both, and first-by-start-time wins (decision 25). A data-entry mistake, not a rule
  to write.
- **Per-variant sold-out** — decision 9, with its trigger recorded there.
- ~~**Two handlers stamp the same occurrence with different temporal guarantees.**~~ Closed by
  decision 56 — one `phase`, computed once. It was worse than recorded: the point lookup read
  every *past* day as in progress, not merely as ambiguous.

- **The card offers the call-off for the first market of a day only.** `next-menu-card.ts`
  shows `days().find(day => !day.absent)`, so a vendor with two markets on one date gets a
  door for the earlier one. The later one keeps the live screen's door if it has a menu, and
  has none if it does not. Pilot is one vendor with one market a day. **Trigger: a vendor
  schedules two markets on the same date** — at which point the card is the wrong shape for
  the day, not just for this door (decision 25's overlap, one level up).

- **The three outcomes carry no quantity** (slice 2b). Selling 2 of 2 and 18 of 20 both read as
  *sold out*, and a small batch that cleared cannot be told from a large one that did. The
  deliberate trade `MARKET_MIAM.md` made when it superseded the brought/left quantities design —
  the value is the pattern per item across months, not the fidelity of one day.
