Ordering

Ordering is in the only package, 50 € HT a month, with no commission; Stripe's fees on a vendor's payments are the vendor's. The plan is docs/ORDERING-PLAN.md. Agreed rules

All four agreed on 24 October 2026.

R1

Nothing is recorded before Stripe holds the card

Placing an order only opens a Checkout page. Our first event is the webhook saying the card is held. Anonymous traffic never touches the append lock (ADR 0028). An abandoned checkout exists only in Stripe's dashboard.

Saturday noon is about 10 writes a second against a ceiling of 300 to 1 000. The baseline measurement finding M6 asks for is still owed.

R2

Processors call Stripe; webhooks record the outcome

A processor reacts to one of our events, calls Stripe, and writes nothing. Stripe's outcomes enter our log only through webhooks: checkout, capture, cancellation, refund. No write ever waits on Stripe.

Each request uses the order ID as its idempotency key, so a retry cannot act twice. Stripe keeps keys for at least 24 hours. A call refused for good still needs a path (Q5).

R3

Stripe onboarding is prefilled from the mentions légales

We create the vendor's Stripe account with what we already hold: business type, legal name, address, SIRET, TVA number, contacts and legal representative from the mentions légales, name and URL from the storefront, the caterer activity code. Stripe asks only for the rest: IBAN, the representative's date of birth, home address and ID, a société's owners.

Prefilling is one shot. Once the first onboarding link exists, we can no longer read or write the account's verification details; later changes go through the vendor's Stripe dashboard (Q9). The live client fills in their mentions légales first.

R4

A storefront is published only once its Stripe account can take payments

Every published storefront takes orders, so a Stripe account able to take payments is a publication requirement, after the legal identity it is prefilled from. Setup order: mentions légales, Stripe, publish.

Like the legal-identity gate, this applies at publication and never takes down a live storefront. The live client is already published and will connect Stripe later, by a route not yet designed. An ADR amending 0031's requirements table comes with the build.

Calls with no login

All three land on apps/api, next to the public storefront route.

CallFromProtection
Place an order Customer's browser
  • The browser sends dish IDs and quantities. The server prices them from the day's menu and applies the 119,99 € cap
  • The day must be live and open, the dishes on its menu and not sold out, the vendor able to take payments
  • Rate limit per IP, from Render's forwarded header
Order status Customer's browser A long random token in the link, never the order number, plus a rate limit
Webhooks Stripe Stripe's signature, plus the idempotency gate against replays

No captcha of our own until the first real abuse: Checkout already has one, and ours would add a third party and a privacy-policy line. A double tap needs nothing: the second Checkout page expires unfinished.
