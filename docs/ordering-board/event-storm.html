Agreed rules

R1

Nothing is recorded before Stripe holds the card

  • Placing an order only asks Stripe for a Checkout page. The first fact on our side is order placed: card held, recorded from Stripe's webhook.
  • Why: an anonymous customer can't put anything in front of a vendor, or into the event log, without a real card held. Every write takes the global append lock (ADR 0028), so a flood of writes would slow every vendor down.
  • Cost: an abandoned checkout leaves no trace on our side, only in Stripe's dashboard.

Agreed 24 October 2026

R2

Processors call Stripe; webhooks record the outcome

  • A processor reacts to one of our events, calls Stripe, and stops. It writes nothing, so it never holds the append lock while waiting on Stripe.
  • Stripe's outcomes enter our log only through webhooks: checkout, capture, cancellation, refunds. The plan already said it for checkout; this extends it to every Stripe interaction.
  • Needs: one Stripe idempotency key per request, the order ID, so a retry can't act twice (Q10), and a path for a call refused for good (Q5).

Agreed 24 October 2026

R3

Payment onboarding comes after the mentions légales, and is prefilled from them

  • We create the vendor's Stripe account already filled in: business type, legal name, address, SIRET, TVA number, contacts and legal representative from the mentions légales; name and URL from the storefront; the caterer activity code for everyone.
  • Stripe then asks only for what we don't hold: the IBAN, the representative's date of birth, home address and ID document, and a société's owners. The vendor never types the same thing twice.
  • Order: every storefront published since the readiness gate has mentions légales. The live client fills theirs in first.
  • Limit: prefilling is one-shot. Once the first onboarding link exists on a Standard account, we can no longer read or write its verification details. Later changes reach Stripe only through the vendor's own dashboard (Q11).

Agreed 24 October 2026

R4

A storefront is published only once its Stripe account can take payments

  • Ordering is in the only package, so every published storefront takes orders. A Stripe account able to take payments joins the publication requirements, after the legal identity it is prefilled from (R3).
  • Setup order: mentions légales, then Stripe, then publish.
  • The live client stays published and connects Stripe afterwards, through a temporary way in to be designed. Like the legal-identity gate, the requirement applies when publishing, so it doesn't take down a storefront that is already live.
  • Later: an ADR amending 0031's table of publication requirements, when it is built.

Agreed 24 October 2026

R2 on one example: capture

Each direction goes one way. Only the two outer steps write to our log, and neither waits on Stripe.

  1. Order acceptedVendor's tap. Short write

  2. Whenever an order is accepted, capture its paymentProcessor. Writes nothing

  3. Stripe captures the held paymentOutside our system

  4. Payment takenWebhook. Short write

  5. Whenever the payment is taken, send the customer their codeProcessor

Calls with no login behind them

All three land on apps/api, next to the public storefront route the customer frontend already calls. The vendor's calls stay behind the existing login.

Notes

The append lock

  • Ordering's Saturday-noon estimate is about 10 writes a second, against a ceiling of roughly 300 to 1 000 (ADR 0028).
  • R1 keeps anonymous traffic away from the lock. R2 keeps Stripe calls out of it, so no ordering write waits on an outside service.
  • Next: the baseline measurement finding M6 asked for, so the ceiling is a number rather than an estimate.
